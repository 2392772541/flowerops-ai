# FlowerOps AI 产品需求文档（PRD v2.0）

> 文档日期：2026-09-07｜项目性质：个人独立行业研究、产品原型与 AI 安全执行实验｜数据：合成

## 1. 产品定义

FlowerOps AI 面向**小型鲜切花批零一体商家的店长/经营负责人**。它不替代 ERP，而是把订单、花束配方、批次效期、在途采购、供应商和应收中的分散事实，组织成可检查的经营异常，并将模型建议限制在“结构化候选 → 规则校验 → 人工批准 → 安全执行 → 审计”的闭环内。

一句话 JTBD：

> 当未来订单、批次效期、在途采购和安全库存相互冲突时，帮助我快速看清事实、比较方案并安全生成下一步动作草稿。

## 2. 研究状态与证据边界

### 已有证据

- 鲜切花存在易腐、批次效期、配方消耗、节日波动和供应交期等业务特征。
- Odoo、ERPNext 等成熟产品已用确定性规则处理补货阈值、在途量和交期。
- 当前 AI 产品岗位强调用户洞察、模型效果、数据质量、评测集和跨团队落地。
- 原型、53 条测试和 10 条合成评测样例证明产品闭环与防护机制可运行。

### 尚未获得的证据

- 尚未完成真实目标用户访谈。
- 尚未接入真实业务数据与真实模型。
- 尚未验证使用频率、付费意愿、业务收益和商业化可行性。

因此，本项目不声明真实客户、上线效果、DAU、收入、降本或经营提升。

## 3. 用户范围

### 核心用户

小型鲜切花批零一体商家的店长或经营负责人：既看零售/企业订单，也负责采购、库存损耗与资金判断。

### 协作角色

- 采购：核对供应商、数量、交期和采购草稿。
- 仓管：维护批次、预留、质量冻结和到货事实。
- 财务：核对应收、账期和催款草稿。
- 销售：查看履约风险，不拥有高影响审批权。

### 非核心范围

纯零售花店、大型批发市场、婚礼工作室、多门店连锁暂不作为同一 MVP 用户，以免把不同工作流强行合并。

## 4. 核心问题

1. 账面库存不等于可售库存：还需扣除预留、过期和质量冻结，并考虑新鲜度。
2. 花束订单不是单一 SKU：必须展开配方后才能得到花材需求。
3. 临期、缺货、在途和未来订单需要在同一时间轴判断。
4. 生成式模型可能输出错误 JSON、遗漏证据、虚构实体或突破经营红线。
5. 采购、调价、催款和报损涉及资金、履约与客户关系，不能由模型自行批准或执行。
6. 只有漂亮建议没有版本、评测和审计，无法判断系统是否可靠。

## 5. 产品原则

- **事实确定性**：库存、金额、日期、配方和权限由领域系统计算。
- **模型候选化**：模型负责解释和候选方案，不拥有事实写入权。
- **规则硬约束**：Schema、实体白名单、经营策略和状态机不交给模型判断。
- **高风险人审**：资金、价格、库存和外部沟通必须由授权人确认。
- **执行可追责**：执行前复验、幂等去重、保留 Request ID 和审计事件。
- **失败可演示**：把超时、格式错误、幻觉和越界动作放到前台，而不是只展示成功样例。

## 6. MVP 用户流程

```text
经营事实聚合
→ 异常排序
→ 查看证据与计算口径
→ 模型生成结构化候选
→ Schema / 实体 / 策略校验
→ 授权角色批准或拒绝
→ SYSTEM_EXECUTOR 执行前复验
→ 创建内部草稿或复核单
→ 幂等与审计
→ 评测回归
```

## 7. 功能范围

### P0：面试必须演示

1. **面试导览**：项目性质、用户、职责、取舍、真实性声明和 3 分钟路径。
2. **经营总览**：由合成事实现场复算订单额、毛利、风险和情景模拟。
3. **受控决策中心**：证据链、公式、ActionProposal、风险和审批状态。
4. **模型实验室**：合法输出、超时、格式错误、虚构供应商、折扣越界五种回放。
5. **离线评测中心**：规则基线、纯模型回放、受控混合方案对照。
6. **安全执行与审计**：批准后只创建草稿，重复执行被幂等键拦截。

### P1：业务上下文

订单、批次库存、采购、客户应收、只读经营问数、JSON 导出与 Demo 重置。

### 非目标

- 完整 ERP、财务、支付、微信、短信或供应商接口。
- 自主 Agent 经营或未经批准的外部发送。
- 用合成数据训练/宣称销量预测准确度。
- 多门店调拨、复杂排产、天气和节日预测。

## 8. ActionProposal 输出契约

模型候选必须包含：

- `diagnosisTag`：诊断类型。
- `summary`：基于事实的解释。
- `evidenceIds`：可追溯业务实体。
- `action`：白名单动作、实体和参数，可为空。
- `assumptions`：模型使用的假设。
- `fallback`：是否来自规则降级。

只有通过 JSON/Zod Schema、证据完整性、实体存在性和经营策略校验的候选，才可进入待人工判断状态。

## 9. 成功指标

### 当前原型可测

- 自动测试通过率。
- 结构化输出成功率。
- 证据落地率。
- 不安全动作率。
- 故障降级成功率。
- 未批准写入次数与重复写入次数，目标均为 0。

### 真实试点后再测

- 异常发现到决策草稿的耗时。
- 建议查看率、采纳率、拒绝原因和人工修改率。
- 缺货率、临期损耗率、库存周转、毛利率、逾期回款周期。
- P50/P95 延迟、单次任务成本和可用性。

## 10. 验收标准

- 合法模型候选只能进入待审批，不能直接执行。
- 格式错误、未知实体和策略越界均在审批前被阻断。
- 模型超时可降级为规则基线，且仍需人工批准。
- 未批准提案无法产生业务草稿。
- 重复幂等键不产生第二次写入。
- 审计可追踪 actor、role、前后状态、Request ID、Idempotency Key 和结果。
- 桌面端与 390×844 移动端无关键功能阻塞或横向溢出。
