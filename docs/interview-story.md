# AI 产品经理面试讲解脚本

## 30 秒版本

我做的是 FlowerOps AI，一个面向鲜切花批发、社区花店和花艺工作室的经营决策工作台。鲜花库存会随时间快速贬值，传统库存数量不能直接代表真实可售能力。我把订单、花束配方、批次效期、供应商、采购和应收连接成经营事实层，让 AI 发现缺货、损耗和回款风险，并生成带证据的业务动作提案。考虑到采购、调价、催款和报损会影响资金及履约，我把 AI 限制为只读分析和提案生成，必须经过人工审批、执行前复验、幂等执行和审计追踪才能进入业务系统。

## 一分钟版本

这个项目不是聊天机器人，而是一套完整的 B 端 AI 决策闭环。系统首先从订单、库存批次、供应商交期和客户应收中计算经营事实；规则 AI 根据透明规则识别异常，展示证据链、预期影响和将要执行的结构化载荷；店长或对应业务角色负责批准，`SYSTEM_EXECUTOR` 在执行前重新进行 Schema、业务实体和权限校验，成功后只创建采购草稿或复核单，并记录操作人、角色、前后状态、Request ID 和 Idempotency Key。这样既体现 AI 带来的决策效率，也明确了模型输出不确定性下的责任边界。

## 五分钟现场演示

### 1. 经营总览：先讲业务问题

指出三个经营风险：

- 周末订单导致红玫瑰预测缺货。
- 临期批次仍有较多可售库存，存在损耗风险。
- 企业客户存在逾期应收，需要分级跟进。

关键表达：系统不是让用户先向 AI 提问，而是主动把最紧迫的问题排成经营优先级。

### 2. AI 决策中心：展示为什么建议补货

打开“补充 260 枝红玫瑰”提案，讲清：

- 未来需求 342 枝。
- 有效库存 356 枝。
- 安全库存 180 枝。
- 预测采用透明、可复现规则，不包装成未经验证的智能算法。
- 页面提前展示将写入的结构化 Payload 和预计影响。

### 3. 权限边界：体现 AI 产品治理

强调三种身份：

| 身份 | 职责 |
|---|---|
| `AI_AGENT` | 读取数据、诊断问题、生成 ActionProposal |
| `MANAGER` | 核对证据、预算和风险并批准或拒绝 |
| `SYSTEM_EXECUTOR` | 对已批准提案二次校验并执行受控动作 |

AI 不能审批自己的建议，也不能直接覆盖库存或自动发送采购单。

### 4. 安全执行：展示完整闭环

点击“店长批准”，再点击“安全执行”。随后进入采购中心，证明系统只创建 `DRAFT` 采购草稿，没有伪装成已向供应商下单。

### 5. 审计中心：展示可追溯性

展示：

- `PROPOSAL_APPROVED`
- `PROPOSAL_EXECUTED`
- `MANAGER`
- `SYSTEM_EXECUTOR`
- Request ID
- Idempotency Key
- 操作前后状态

最后说明相同幂等键重复提交不会产生第二张采购单。

## 为什么选择鲜切花

鲜切花同时具有易腐、批次管理、配方消耗、节日波动、供应商交期和企业客户账期等特点。它能在个人项目可控制的范围内，展示比普通库存管理更复杂、更适合 AI 辅助决策的业务问题。

## 关键产品取舍

### 为什么不直接接大模型

当前版本使用固定规则 Provider，目的是先验证业务闭环、权限、执行和评测框架。直接接模型会让演示依赖 API Key、网络和随机输出，也容易掩盖业务规则缺陷。

### 为什么 AI 不直接执行

模型输出是概率性的，而采购、库存、调价和应收操作涉及资金、履约与客户关系。AI 负责收集证据、缩小决策范围，人类负责高影响决策，系统执行器负责确定性写入。

### 为什么使用合成数据

个人作品集不应虚构真实客户、收入和降本结果。合成数据用于验证产品逻辑；真实上线后再通过试点建立基线指标和业务收益。

## 面试官可能追问

**预测靠谱吗？**
Demo 使用透明规则。真实上线前需要接入历史销量、节日、天气、价格、促销和缺货数据，按时间窗口做离线回测，再与人工采购基线比较。

**如何接真实大模型？**
通过服务端 `AIProvider` 适配层接入模型，密钥不进入浏览器。模型负责解释和结构化提案，库存计算、权限、校验和业务写入仍由确定性领域服务完成。

**如何衡量价值？**
先采集人工决策耗时、临期损耗率、缺货率、采购修改率和逾期回款周期作为基线，再通过灰度试点比较 AI 建议采纳率、人工修改率和经营指标变化，不提前捏造收益数字。

**如果模型生成不存在的供应商怎么办？**
执行前的业务实体校验会拒绝不存在的供应商、商品、客户和批次；供应商与商品供货关系不匹配也无法获批。

**如何避免重复下单？**
每个提案带 Idempotency Key。执行服务记录已处理键，相同键再次提交时只写审计，不产生第二次业务写入。
